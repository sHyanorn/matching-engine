machine: a cloud VM, Intel(R) Xeon(R) Processor @ 2.30GHz, 4 vCPUs (lscpu: 4
  cores, 1 thread per core), 15.7 GiB, KVM, no cpufreq governor exposed,
  idle but for the runs; the same VM as bench-results/core-reuse. The
  harness pins its matching thread to CPU 2 and its draining thread to
  CPU 3 (its defaults), leaving CPUs 0 and 1 to the system and the Go
  runtime. Neighbours on the host are not under our control.
  Every number here is from this VM. Compare engines with each other only
  within this directory: the flash1-dev benchmark's published tables
  were measured on Graviton4 (Neoverse-V2) and are not comparable.
os: Linux 6.18.44-fc-v470 x86_64
go: go1.27.4 linux/amd64
compilers: the harness with Ubuntu clang 18.1.3 (cmake 3.28.3); the
  reference adapters with g++ 13.3.0, as the benchmark's build scripts
  call it (-std=c++20 -O3 -march=native -fPIC -shared); our adapter with
  go build -buildmode=c-shared
packages: libboost-dev 1.83.0.1ubuntu2 (harness transport), libfmt-dev
  9.1.0+ds1-2 (CppTrader's CppCommon at e14011974b8d, which follows the
  main branch of {fmt} without pinning a version)

adapter/: the adapter's delivery and report paths. Ten alternating runs
  of each variant on normal; summary.txt has the medians. no-batch.diff
  and push-each.diff apply to cmd/harness-adapter/main.go.

conformance.txt and audit-*.txt: scripts/harness.sh cases, 2026-11-14
  12:18:30 to 12:24:45 UTC. Per case: whether Liquibook, CppTrader and
  geseq/orderbook produced the same canonical report stream, whether this
  engine's equals it, and the state audit of this engine, CppTrader and
  geseq against Liquibook. Then the audit on the five scenarios at seed
  23. geseq's audits pass the hash and the state checks, but the harness
  calls them INVALID because its probes took over 25% of the timed window
  (50.3% on normal): the benchmark's geseq adapter answers depth queries
  by scanning a map of every order it has seen.

versions.txt: the commits and tools every build was made from.

runs/ and summary.txt: scripts/harness.sh perf, rounds 1 to 10,
  2026-11-14 12:36:39 to 13:03:45 UTC, then scripts/harness.sh summary.
  Each round runs every engine once on each of the five scenarios (seed
  23, 1M orders, about 2M messages), one engine after another, starting
  one engine later each round. An engine's result is its lowest scenario
  median, as the benchmark defines it. Every run's report stream had the
  published hash. geseq's runs are all INVALID, for the probe time noted
  above, so its throughput is not a valid result of the benchmark.
noise: the same binary on the same scenario varied by 1.20x to 1.46x
  over its 10 runs (this engine) and up to 2.09x (CppTrader, Liquibook),
  so only the medians and the run-by-run comparison in summary.txt mean
  anything here, and only as a ranking on this VM. Tails and absolute
  figures need a quieter machine.
